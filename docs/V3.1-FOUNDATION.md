# v3.1 implementation foundation

## Validation execution

Each behavioral dimension now has a separate command:

```text
persona-lab coherence
persona-lab abstention
persona-lab framing_resistance
persona-lab distinctiveness
persona-lab backtest
```

For live runs, the persona model generates the response and the independent
judge model evaluates it against a versioned rubric. A dimension can report
PASS only from the actual judge response. Mock commands are plumbing only:
they report `MOCK`, do not preserve mock verdicts, and do not update a persona
registry. Validation dimensions remain separate and no aggregate validity
percentage is computed.

Results pin the persona and judge prompt versions, rubric, probe design,
harness, generation parameters, model deployments, and persona file hash.
Distinctiveness results also pin each comparison persona hash.

Backtest requires an explicit comparison-design file. The controlled
backtest implementation reads holdout and sends it only to the evaluator;
persona generation receives the pinned persona and declared prompt, never
the held-out answer. If a held-out result informs a persona or methodology
revision, the contamination ledger records the holdout ID and revised
approach hash; those records are excluded when validating that approach.

## Study execution snapshot

`scripts/snapshot_study.py` freezes an approved study's persona hashes and
validation profiles, method and research-report contract versions, execution
provider/model, run count, and limitations, then transitions it to `running`.
A snapshot is write-once and is not recalculated when validation changes. The service marks newly snapshotted
studies as format `3.1`; the checker requires a snapshot for 3.1 studies once
they are running or complete. `execution_snapshot` remains optional for
unversioned v3 studies created before this change.

## Model-call token telemetry

Validation calls append metadata-only JSONL records with operation, provider,
model/deployment, input/output token counts when supplied by the provider,
and relevant persona, study, and client IDs. Prompts, responses, and secrets
are excluded.

### Token-efficiency opportunities (estimates)

In the current blind-interview pattern, each question call repeats the
transcript to date. For a 12-question run, the history occupies 66
question/answer-turn positions across calls (1+2+...+11 prior turns), versus
11 positions in the final transcript. Thus 55 positions are repeated after
their first inclusion, about 83% of transmitted history positions. This is
a structural estimate, not provider-measured tokens; exact savings depend
on response lengths, system/persona prompts, and provider caching.

Planned opportunities, not implemented in this increment:

- Compiled runtime personas could avoid repeatedly transmitting authoring
  scaffolding and duplicate detail.
- Compact interview-state context could reduce repeated history toward a
  fixed summary; savings vary with summary fidelity and transcript length.
- Hash-based context caching may reduce billed input on providers that
  support prompt caching; it does not reduce bytes by itself.
- Incremental evidence processing could avoid re-reading unchanged evidence.
- Configurable model-routing policy could reserve larger/stronger models for
  selected tasks, subject to client approval and evaluation.

These are design directions, not benchmarked savings or an approved routing
policy.

## Shared application boundary

`research_os.application` defines repository interfaces and thin filesystem
services for clients, evidence, personas, insights, validation, studies, and
reports. The filesystem is still the persistence layer. Future CLI, Copilot,
Claude, and UI adapters should call the same service layer; no UI or alternate
storage backend is included here.
